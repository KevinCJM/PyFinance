# MetricsFactory Skill 详细设计

## 目标

将本项目的指标计算能力封装成 `metrics-factory` skill，让后续智能体在处理金融产品指标计算、指标清单查询、复权净值口径检查、区间/滚动参数确认、指标新增和调试时，不必重新完整阅读四个业务脚本。

skill 的核心职责不是替代源码，而是给智能体提供正确的入口、硬约束、风险提醒和验证流程。

## 设计原则

- `SKILL.md` 只放智能体执行任务时必须立即知道的信息。
- 完整指标清单、窗口映射、长公式和示例数据放入 `references/` 或由 `scripts/` 动态生成。
- 对会静默污染计算结果的约束，用强规则表达，不写成普通建议。
- 配置说明不等于真实实现。解释公式或修改指标时必须回到 `period_metrics_cal.py` / `rolling_metrics_cal.py` 核对。

## Skill 触发范围

`metrics-factory` 应在以下任务中触发：

- 查询支持哪些区间指标、滚动指标、区间代码、滚动窗口。
- 使用宽表 DataFrame 计算区间指标或滚动指标。
- 检查输入数据格式、复权净值口径、OHLCV 口径一致性。
- 解释某个指标结果、排查指标为 NaN、行数减少或结果异常。
- 新增、删除、修改区间指标或滚动指标。
- 调试 `metrics_cal_config.py` 与计算类分派不一致的问题。

不应把该 skill 当成外部行情下载、数据清洗平台或交易系统 skill。它只覆盖本目录内 MetricsFactory 指标计算工具。

## SKILL.md 必须写入的信息

### P0：阻断级必要信息

#### 1. Source Of Truth

必须写入：

- 真实计算行为以 `metrics_factory.py`、`period_metrics_cal.py`、`rolling_metrics_cal.py` 为准。
- `metrics_cal_config.py` 管理指标名、中文说明和默认映射，但其中的公式文案不能单独作为最终实现依据。
- 回答指标含义或修改指标前，应核对对应 `cal_*` 函数和特殊分派逻辑。

理由：

- 例如 `TotalReturn` 默认是对数收益累加，而配置文案容易让智能体误以为是简单收益率。
- VaR、Percentile、CrossProductRatio、MaxDrawDown、KRatio、NetEquitySlope 等存在字符串特殊分派，不能只按函数名猜。

#### 2. 硬入口契约

必须写入：

- 区间入口：`compute_metrics_for_period_initialize(...)`。
- 滚动入口：`compute_all_rolling_metrics(...)`。
- 区间入口按区间写出 `{period}.parquet`。
- 滚动入口写出 `rolling_metrics.parquet`。
- 两个入口都不返回最终结果文件；结果从 `save_path` 读取。
- `save_path` 必须已存在，代码不会负责创建目录。

理由：

- 智能体容易写成 `df = compute_metrics_for_period_initialize(...)` 并期望返回 DataFrame。
- `to_parquet()` 依赖目录存在和本地 parquet 引擎，运行前要明确输出路径。

#### 3. 硬输入契约

必须写入：

- 所有输入都是宽表 `pandas.DataFrame`。
- index 必须是升序日期。
- columns 必须是产品代码。
- 所有输入表必须同 index、同 columns、同顺序。
- 代码大量使用 `.values`，不会自动按 index/columns 对齐。

理由：

- 输入错位不会一定报错，而是静默污染收益、回撤、滚动指标。
- `fund_list` 是直接列选择，不存在的产品代码会触发 KeyError。

#### 4. 复权净值口径

必须写入：

- 强烈要求 `close_price_df` 使用复权净值或复权收盘价。
- `log_return_df` 必须由同一口径的 `close_price_df` 生成。
- `open/high/low/close` 必须保持同一复权口径。
- 不要混用单位净值、累计净值、未复权价格。
- 只有净值产品没有 OHLC 时，可以临时用复权净值填充 OHLC，但 AR/BR/DKX/CCI 等价格形态指标解释性会下降。
- 无真实成交量时，不应解释 `Vol*`、`OBV`、`PVT`、`VR` 等成交量指标。

理由：

- 收益、回撤、净值斜率、新高率、KDJ、均线、DKX 等都会被混口径污染。
- 成交量类指标依赖真实成交量，填充值会导致结论失真。

#### 5. 区间真实执行规则

必须写入：

- 默认遍历 `period_list`，但只有 `create_period_metrics_map()` 中存在映射的区间才会计算。
- 默认 `period_list` 包含 `3y`、`5y`、`mtd`、`qtd`、`ytd`、`max`，但当前没有指标映射，默认会跳过。
- `30d`、`35d`、`70d` 有指标映射，但不在默认 `period_list`，需要显式传入 `p_list`。
- `Nd` 区间按交易日索引截取。
- `Nm/Ny/mtd/qtd/ytd` 通过 `get_start_date()` 按自然日边界计算。
- `spec_end_date` 必须是交易日，且建议先校验在输入 index 中。

理由：

- 用户问 “5d” 和 “5m” 时，窗口含义完全不同。
- 智能体容易误以为默认列表全部产出，或误以为配置里出现的所有区间默认都会跑。

#### 6. Rolling open/close 阻断风险

必须写入为强风险：

- `compute_all_rolling_metrics()` 当前调用 `CalRollingMetrics` 时传入顺序为 `open_price_array, close_price_array`。
- `CalRollingMetrics.__init__()` 的签名期望顺序为 `close_price_array, open_price_array`。
- 这意味着 `self.price_array` 和 `self.open_array` 可能互换。
- 所有依赖收盘价/开盘价的滚动指标在修复或验证前不能直接信任。

必须写入处理流程：

- 如果只是解释结果，先明确该风险。
- 如果要生产使用，先修复或构造 open 与 close 刻意不同的小样本做对照验证。
- 至少验证 `CloseMA`、`EMA`、`KDJ`、`VR`、`OBV`、`AR`、`BR`、`DKX`。

理由：

- 这不是普通解释性下降，而是核心价格输入可能错位。
- KDJ、VR、OBV 都使用 `self.price_array`，会受 open/close 错位影响。

#### 7. 未接入配置

必须写入：

- `log_return_relative_metrics_dict` 当前没有接入公共入口。
- `long_short_metrics` 当前没有接入 `create_rolling_metrics_map()`，计算类也没有公开分派。
- 不要因为配置字典里存在 `BBI`、`DMA`、`DIF`、`DEA`、`MACD`、`ADXSlop-6` 就声称可直接计算。

理由：

- 智能体容易把“配置存在”误判成“入口可用”。

### P1：执行级必要信息

#### 1. 参数使用细节

必须写入：

- `fund_list` 是直接列筛选，不会自动忽略不存在的列。
- `metrics_list` 不会自动按 period/window 过滤，传错指标可能只打印错误、跳过，最后报“没有计算出任何指标”。
- `min_data_required` 默认 2。
- 区间计算还会用 `first_valid_dates <= start_date` 过滤产品，新产品或数据不足会被过滤或输出 NaN。
- 滚动入口的 `num_workers` 参数当前未实际参与并行。

理由：

- 这些是排查“为什么没结果、为什么行少、为什么没提速”的高频坑。

#### 2. Rolling 窗口细节

必须写入：

- `roll_list` 应来自 `create_rolling_metrics_map().keys()`。
- 支持窗口为 `0, 3, 4, 5, 6, 7, 8, 9, 10, 12, 14, 15, 19, 20, 22, 25, 26, 30, 35, 60, 99`。
- `0` 只对应无需滚动窗口的 `OBV`、`PVT`、`TR`。
- 同一窗口内 rolling 指标通过 outer merge 合并。
- 不同窗口结果最终通过 inner merge 合并，可能收缩日期/产品组合。

理由：

- 非法窗口会 KeyError 或无结果。
- 用户排查 rolling 输出行数减少时，需要知道 inner merge 行为。

#### 3. 最小调用模板

必须写入简洁模板：

```python
from MetricsFactory.metrics_factory import compute_metrics_for_period_initialize

compute_metrics_for_period_initialize(
    log_return_df=log_return_df,
    close_price_df=close_price_df,
    high_price_df=high_price_df,
    low_price_df=low_price_df,
    volume_df=volume_df,
    save_path=save_path,
    p_list=["25d"],
    spec_end_date=None,
    multi_process=False,
)
```

```python
from MetricsFactory.metrics_factory import compute_all_rolling_metrics

compute_all_rolling_metrics(
    open_price_df=open_price_df,
    close_price_df=close_price_df,
    high_price_df=high_price_df,
    low_price_df=low_price_df,
    volume_df=volume_df,
    save_path=save_path,
    roll_list=[5, 10, 20],
)
```

理由：

- 当前 skill 只有入口名，没有可执行调用形状。
- 模板能显著减少智能体构造错误参数的概率。

#### 4. 新增/修改指标 checklist

必须写入：

区间指标：

- 在 `metrics_cal_config.py` 的 `log_return_metrics_dict` 增加指标、说明、支持区间。
- 在 `period_metrics_cal.py` 增加 `cal_<MetricName>` 或更新 `cal_metric()` 特殊分派。
- 如果是 `VaR-*`、`CVaR-*`、`Percentile-*`、`TailRatio-*`、`CrossProductRatio-*` 这类动态名称，要确认字符串解析逻辑。
- 运行 catalog 导出，确认指标进入对应区间。

滚动指标：

- 在 `rolling_metrics` 增加指标、说明、支持 rolling days。
- 在 `rolling_metrics_cal.py` 增加 `cal_<MetricName>` 或更新 `cal_metric()` 前缀分派。
- 对动态名称如 `Boll*`、`KDJ-*`、`MTMMA-*`、`MATRIX-*`、`MACR-*`、`MAVR-*`、`ADX-*`、`ADXR*`、`MADKX*` 必须确认 prefix dispatch。
- 如涉及价格，先处理或验证 open/close 顺序风险。

理由：

- 仅改配置无法让指标可计算。
- 仅写函数但未加入配置映射，也不会默认批量产出。

### P2：解释级信息

可写入较短说明：

- 年化收益天数 `return_ann_factor = 365`。
- 年化波动天数 `risk_ann_factor = 252`。
- 无风险年化收益 `no_risk_ann_return = 0.015`。
- `HurstExponent` 即使配置在 `70d`，有效样本不足时仍会输出 NaN。
- 源码使用 `MetricsFactory.*` 绝对导入；运行示例最好从父目录或正确 `PYTHONPATH` 下执行。
- 当前本机环境可能出现 NumPy import 架构问题，`py_compile` 通过不等于真实 import 和计算通过。

## 不应写入 SKILL.md 的内容

以下内容不应放入 `SKILL.md`，应放到 `references/` 或 `scripts/`：

- 完整 85 个区间指标清单。
- 完整 96 个滚动指标清单。
- 每个区间/窗口到指标列表的完整矩阵。
- 每个指标的完整公式和中文长说明。
- 复权净值样例数据构造 cookbook。
- 指标实现细节审计报告。
- 性能、大数据、多进程、共享内存排障长文档。

理由：

- `SKILL.md` 是触发后立即进入上下文的文件，过长会降低后续任务执行效率。
- 指标清单会随配置变化，动态脚本比静态长列表更可靠。
- 公式文案不一定等于源码实现，长公式容易诱导智能体跳过源码核对。

### Decision Tree 应写什么

- 用户问支持指标：运行 `export_metric_catalog.py`，必要时读 `references/metric-catalog.md`。
- 用户要算区间指标：检查输入对齐、复权口径、`save_path`、`p_list`、`spec_end_date`。
- 用户要算 rolling：先提示 open/close 风险，再检查 OHLCV 口径和 `roll_list`。
- 用户要解释指标：先定位实际 `cal_*` 函数，不只复述配置文案。
- 用户要新增/修复指标：按 checklist 修改配置、实现、分派和 catalog。

## AI 智能体友好入口设计

当前两个业务入口都是 Python 函数，适合人类开发者在代码里调用，但不够适合智能体稳定使用：

- 没有真正的命令行入口，`metrics_factory.py` 的 `if __name__ == '__main__': pass` 不执行任务。
- 智能体需要临时写 glue code 来加载数据、校验输入、创建输出目录、选择区间、选择并发参数，容易引入随机差异。
- 区间入口的 `multi_process` 是全局开关，但最合适的并发判断其实应按每个 period 单独决定。
- 滚动入口虽然有 `num_workers` 参数，但当前没有实际并发。
- 当前没有 dry-run 计划输出，智能体执行前无法清楚说明会计算多少产品、多少区间、多少结束日、写哪些文件、用几个进程。

### 推荐新增入口脚本

建议在 skill 中新增智能体专用脚本：

```text
skills/metrics-factory/scripts/run_metrics_job.py
```

职责：

- 从 JSON 请求文件读取任务。
- 执行输入契约校验。
- 生成 dry-run 计划。
- 根据产品数量、区间数量、结束日数量、指标数量和机器资源自动选择是否并发。
- 调用现有 `metrics_factory.py` 入口完成计算。
- 写出 `run_manifest.json`，记录本次任务、并发决策、跳过项、风险提示和输出文件。

不建议第一阶段直接重写核心计算公式。入口脚本应作为编排层存在，尽量复用现有 `compute_metrics_for_period_initialize(...)` 和 `compute_all_rolling_metrics(...)`。

### 请求文件格式

建议使用 JSON，避免智能体临时拼 Python：

```json
{
  "job_name": "example_period_metrics",
  "mode": "period",
  "data": {
    "log_return": "data/log_return.parquet",
    "close_price": "data/close_price.parquet",
    "open_price": null,
    "high_price": "data/high_price.parquet",
    "low_price": "data/low_price.parquet",
    "volume": "data/volume.parquet"
  },
  "data_contract": {
    "price_basis": "adjusted_nav",
    "ohlc_basis": "same_as_close",
    "volume_basis": "real_or_not_used"
  },
  "selection": {
    "fund_list": null,
    "periods": ["25d", "50d", "6m"],
    "roll_windows": null,
    "metrics": null,
    "spec_end_date": null,
    "min_data_required": 2
  },
  "output": {
    "save_path": "outputs/metrics",
    "overwrite": false
  },
  "parallel": {
    "mode": "auto",
    "max_workers": null,
    "reserve_cores": 1,
    "min_tasks_per_worker": 4,
    "memory_headroom_gb": 2
  }
}
```

字段约束：

- `mode` 支持 `period`、`rolling`、`both`。
- `data_contract.price_basis` 必须显式填写；如果是 `unknown`，脚本应阻断或要求 `--allow-unknown-basis`。
- `save_path` 可以由入口脚本创建，但必须在 manifest 中记录。
- `overwrite=false` 时，如果目标 parquet 已存在，应阻断，避免智能体覆盖旧结果。
- `metrics=null` 表示使用配置中的默认指标；如果显式传入，必须先校验这些指标是否在目标 period/window 可执行。

### V1 请求 Schema 闭环规格

第一版入口脚本应只支持低歧义输入，不做“智能猜测”。推荐把 schema 固定为：

```json
{
  "schema_version": "1.0",
  "job_name": "example_period_metrics",
  "mode": "period",
  "data": {
    "format": "parquet",
    "log_return": "data/log_return.parquet",
    "close_price": "data/close_price.parquet",
    "open_price": null,
    "high_price": "data/high_price.parquet",
    "low_price": "data/low_price.parquet",
    "volume": "data/volume.parquet",
    "date_index": true,
    "date_column": null
  },
  "data_contract": {
    "price_basis": "adjusted_nav",
    "ohlc_basis": "same_as_close",
    "volume_basis": "real_or_not_used"
  },
  "selection": {
    "fund_list": null,
    "periods": ["25d"],
    "roll_windows": null,
    "period_metrics": null,
    "rolling_metrics": null,
    "spec_end_date": null,
    "min_data_required": 2
  },
  "output": {
    "save_path": "outputs/metrics",
    "overwrite": false,
    "run_id": null,
    "atomic_write": true
  },
  "parallel": {
    "mode": "auto",
    "max_workers": null,
    "reserve_cores": 1,
    "min_tasks_per_worker": 4,
    "memory_headroom_gb": 2
  },
  "risk_acceptance": {
    "allow_unknown_basis": false,
    "allow_rolling_open_close_risk": false
  }
}
```

闭环规则：

- `schema_version` 必填；未知版本直接阻断。
- V1 只支持 `format=parquet`。CSV/Excel/pickle/feather 先阻断，避免日期解析和类型推断不一致。
- `date_index=true` 表示 parquet 读取后 index 就是日期；`date_index=false` 时必须提供 `date_column`，脚本读取后用该列设为 index。
- index 必须能转换为 `pd.DatetimeIndex`，必须升序且无重复；否则阻断。
- 所有输入必须是宽表，除日期列外所有列都是产品代码；产品列必须可转为数值。
- 区间模式必填 `log_return`、`close_price`、`high_price`、`low_price`、`volume`。
- 滚动模式必填 `open_price`、`close_price`、`high_price`、`low_price`、`volume`。
- `mode=both` 时同时校验区间和滚动所需输入。
- `selection.period_metrics` 和 `selection.rolling_metrics` 分开，不能再共用一个 `metrics` 字段。
- V1 中 `selection.rolling_metrics` 必须为 `null`；当前 `compute_all_rolling_metrics(...)` 不支持传入滚动指标子集。
- `periods=null` 表示使用当前默认 `period_list` 与映射交集；空列表 `[]` 表示不计算区间。
- `roll_windows=null` 表示使用 `create_rolling_metrics_map().keys()`；空列表 `[]` 表示不计算滚动。
- `fund_list=null` 表示全产品；若提供，所有代码必须存在于所有输入表 columns 中，否则阻断。
- `spec_end_date` 若提供，必须能转成日期，且必须存在于交易日 index 中，否则阻断。

### 风险和阻断等级

入口脚本应把问题分成三类，dry-run 和 manifest 都必须记录：

```text
blocker: 不允许 execute
warning: 允许 execute，但最终回答必须提示
info: 仅记录执行事实
```

阻断项：

- 输入文件不存在。
- schema 版本未知。
- 输入格式不是 V1 支持的 parquet。
- 日期 index 无法解析、乱序、重复。
- 输入表 index/columns 不完全一致。
- 必需输入缺失。
- `save_path` 不可创建或不可写。
- `overwrite=false` 且目标文件已存在。
- `price_basis=unknown` 且 `allow_unknown_basis=false`。
- `mode=rolling` 或 `mode=both` 且 rolling 需要执行，但 open/close 风险未修复且 `allow_rolling_open_close_risk=false`。
- 显式指定的 period/window/metric 不在当前可执行映射中。

警告项：

- `volume_basis` 不是真实成交量，但请求包含成交量类指标。
- `price_basis=unknown` 且 `allow_unknown_basis=true`。
- rolling 执行被允许但 open/close 风险仍未修复。
- 可选 period 在 `period_list` 中但当前无指标映射，会被跳过。
- 本地无法读取可用内存，只能使用保守 worker 上限。

默认决策：

- V1 默认不接受未知复权口径。
- V1 默认不执行存在 open/close 风险的 rolling 生产计算。
- 如果用户明确接受风险，脚本可以执行，但 manifest 必须记录风险接受字段；智能体最终回答不能给出确定性绩效结论。

### 命令行形态

建议入口脚本支持：

```bash
python3 skills/metrics-factory/scripts/run_metrics_job.py --request job.json --dry-run
python3 skills/metrics-factory/scripts/run_metrics_job.py --request job.json --execute
python3 skills/metrics-factory/scripts/run_metrics_job.py --request job.json --execute --allow-unknown-basis
python3 skills/metrics-factory/scripts/run_metrics_job.py --request job.json --execute --allow-rolling-open-close-risk
```

`--dry-run` 必须输出：

- 输入文件是否存在。
- 每个输入 DataFrame 的 shape、index 起止日期、产品数量。
- index/columns 是否完全一致。
- 复权净值口径声明。
- 实际会计算的 period/window。
- 被跳过的 period/window 和原因。
- 预计输出文件。
- 每个 period/window 的并发决策。
- 阻断风险，如 rolling open/close 顺序未修复。
- 最终 `can_execute` 布尔值。

`--execute` 必须先内部生成同一份计划，再执行。执行后写出：

```text
<save_path>/run_manifest.json
```

CLI 参数优先级：

- 命令行风险开关只允许把 request 中的 `risk_acceptance` 从 `false` 提升为 `true`，不能反向覆盖。
- `--dry-run` 不写业务 parquet，只允许写可选的 dry-run JSON 到 stdout。
- `--execute` 遇到 blocker 必须退出非 0。
- 如果同时传 `--dry-run` 和 `--execute`，脚本应阻断，要求二选一。
- 不支持交互式确认；智能体需要在运行前把所有决策写入 request。

### 运行目录和导入路径

当前业务代码使用 `MetricsFactory.*` 绝对导入，智能体入口脚本不能要求用户手动猜 `PYTHONPATH`。V1 入口脚本应自己处理：

- 通过 `Path(__file__).resolve()` 找到项目根目录。
- 将项目父目录加入 `sys.path`，确保 `from MetricsFactory.metrics_factory import ...` 可用。
- 所有 request 中的相对路径都按当前工作目录解析；manifest 中同时记录原始路径和绝对路径。
- dry-run 必须检查 `MetricsFactory.metrics_factory`、`pandas`、`numpy` 是否可 import。
- 如果 NumPy/Pandas 架构不匹配导致 import 失败，`--execute` 必须阻断，不应退化为静态执行。
- `export_metric_catalog.py` 仍保持 AST 静态解析，不依赖业务运行时；`run_metrics_job.py` 是运行入口，必须依赖 pandas/numpy 可用。

Manifest 闭环要求：

- `run_manifest.json` 是审计必需文件；`--execute` 成功但 manifest 写入失败，应视为任务失败。
- dry-run 的计划对象和 execute 写入的 manifest 中 `plan_hash` 必须一致，避免执行计划和展示计划不一致。

- manifest 必须记录每个输出文件的路径、行数、列数、文件大小和是否覆盖。
- manifest 必须记录 `blockers`、`warnings`、`risk_acceptance`，即使列表为空。

### 输出和可恢复性

输出目录策略：

- 如果 `output.run_id` 为空，默认使用 `job_name + 规范化请求 hash` 生成确定性子目录，保证同一 request 的 dry-run 与 execute 指向同一计划。
- 实际写入目录建议为 `<save_path>/<run_id>/`，避免不同任务互相覆盖。
- 如果用户明确要求兼容当前核心函数的输出结构，可以设置 `run_id="."`，但这时必须更严格检查覆盖。

原子写策略：

- `atomic_write=true` 时，先写到 `<save_path>/<run_id>/.tmp/`。
- 所有目标 parquet 和 manifest 成功后，再移动到最终目录。
- 如果中途失败，保留 `.tmp/failed_<timestamp>/` 并在错误信息里说明。
- `overwrite=false` 时，最终目录中任一目标文件存在都阻断。
- `overwrite=true` 时，先把旧文件移动到 `<save_path>/<run_id>/.backup_<timestamp>/`，再写新文件。

这能让智能体在失败后明确回答：

- 哪些文件已经生成。
- 哪些文件没有生成。
- 是否覆盖了旧结果。
- 是否可以安全重跑。

### V1 默认决策矩阵

为了让实现可以推进，以下决策作为 V1 默认值；只有用户明确要求改变时才调整：

| 决策点 | V1 默认 | 原因 |
| --- | --- | --- |
| 核心公式 | 不重写 | 降低指标口径变化风险 |
| 区间计算 | 复用 `compute_metrics_for_period_initialize(...)` | 当前已有多进程和 parquet 输出 |
| 区间调度 | 入口脚本按 period 单独调用 | 支持每个 period 独立并发决策和 manifest |
| 滚动计算 | 默认阻断生产执行，除非显式接受 open/close 风险 | 当前 open/close 参数顺序风险未修复 |
| 滚动并发 | V1 不实现 | 当前 `num_workers` 不生效，先避免假并发 |
| 输入格式 | 只支持 parquet | 避免 AI 对 CSV 日期和类型做隐式猜测 |
| 未知复权口径 | 默认阻断 | 避免输出看似精确但口径错误的绩效结果 |
| 输出覆盖 | 默认不覆盖，使用 run_id 子目录 | 避免智能体覆盖历史结果 |
| manifest | 必需 | 没有 manifest 就没有可审计执行记录 |
| 并发阈值 | 先用经验阈值，manifest 记录依据 | 后续可用真实 benchmark 校准 |

因此，实现 V1 不再需要额外人类决策；人类只需要提供：

- 输入 parquet 路径。
- 计算模式：`period`、`rolling` 或 `both`。
- 产品范围、区间/window、指标选择；不提供则走默认。
- 明确的复权口径声明。
- 输出目录。
- 是否接受 unknown basis 或 rolling open/close 风险。

## 自动并发决策设计

### 当前真实并发粒度

必须让智能体知道当前实现的并发边界：

- 区间指标当前可以多进程。
- 区间指标的并发粒度是同一个 period 内的多个 `end_date`。
- 当前实现不是按产品并发，也不是按多个 period 并发。
- `spec_end_date` 存在时，每个 period 通常只有 1 个 end-date task，开进程池大概率得不偿失。
- 产品数量会增加每个 task 的计算成本和内存压力，但产品数量本身不会让当前区间入口产生更多进程任务。
- 滚动指标当前没有真实并发，`num_workers` 只是被赋值，没有用于 `Pool` 或其他并行执行。

### 并发判断必须使用的维度

智能体不应只看产品数量或区间数量。入口脚本应计算：

- `product_count`：实际参与计算的产品列数。
- `trading_day_count`：输入交易日数量。
- `period_count`：实际可执行的区间数量，不包括没有映射而被跳过的区间。
- `valid_end_dates_by_period`：每个 period 实际可计算的结束日数量。
- `metric_count_by_period`：每个 period 实际计算的指标数量。
- `roll_window_count`：实际可执行的 rolling window 数量。
- `metric_count_by_roll_window`：每个 rolling window 实际计算的指标数量。
- `estimated_array_bytes`：输入数组转换为 numpy 后的估算字节数。
- `cpu_count`：机器 CPU 核数。
- `available_memory`：能读取时使用 `psutil.virtual_memory().available`，不能读取时只做保守 CPU 决策并记录 `memory_unknown`。

### 区间指标自动并发规则

第一阶段建议不要一次把多个 period 传给 `compute_metrics_for_period_initialize(...)` 并使用同一个 `multi_process` 决策。更适合智能体的做法是：

- 入口脚本按 period 循环。
- 每次调用 `compute_metrics_for_period_initialize(..., p_list=[period], multi_process=<decision>, num_workers=<decision>)`。
- 每个 period 独立生成并发决策和 manifest 记录。

初始规则：

```text
valid_end_dates = 实际能计算该 period 的结束日数量
metric_count = metrics_list 数量或 period_metrics_map[period] 数量
work_units = valid_end_dates * product_count * metric_count
```

推荐 worker 数：

```text
cpu_cap = max(1, cpu_count - reserve_cores)
task_cap = max(1, floor(valid_end_dates / min_tasks_per_worker))
user_cap = max_workers if max_workers else cpu_cap
memory_cap = 根据 available_memory 和 estimated_array_bytes 保守估算
workers = max(1, min(cpu_cap, task_cap, user_cap, memory_cap))
```

并发开关必须在 worker 计算之后判断：

```text
if parallel.mode == "off":
    multi_process = false
    workers = 1
elif spec_end_date is not null:
    multi_process = false
    workers = 1
elif workers < 2:
    multi_process = false
elif parallel.mode == "on":
    multi_process = true
elif valid_end_dates < 8:
    multi_process = false
    workers = 1
elif work_units < 200000:
    multi_process = false
    workers = 1
else:
    multi_process = true
```

`parallel.mode` 取值：

- `auto`：按上述阈值自动判断。
- `off`：强制单进程。
- `on`：在 `spec_end_date` 不存在且 `workers >= 2` 时强制多进程。

即使 `parallel.mode=on`，也不应在 `spec_end_date` 单日任务上启用多进程，因为当前实现的并发任务数通常只有 1。

初始默认：

- `reserve_cores = 1`。
- `min_tasks_per_worker = 4`。
- `memory_headroom_gb = 2`。
- `work_units` 阈值先用 `200000`，后续用真实耗时校准。

内存估算：

```text
estimated_array_bytes = sum(input_df.values.nbytes after resample)
shared_memory_bytes = estimated_array_bytes
result_pressure_bytes = product_count * metric_count * valid_end_dates * 16 至 64 的粗略系数
```

如果无法可靠估算内存：

- 不因内存未知直接阻断。
- 限制 `workers <= min(cpu_cap, task_cap, 4)`。
- 在 manifest 记录 `memory_unknown_use_conservative_worker_cap`。

### 滚动指标自动并发规则

当前滚动入口不能因为 `num_workers` 自动并发。设计上应分两步：

第一阶段：

- 入口脚本对 rolling 只允许单进程执行。
- manifest 明确写 `rolling_parallel=false` 和原因：`compute_all_rolling_metrics currently ignores num_workers`。
- 如果用户要求强制 rolling 并发，脚本应阻断，而不是假装并发。

第二阶段，在修复 open/close 参数顺序后，再增加 rolling 并发实现：

- 新增 `calc_rolling_shared_worker`。
- 用 shared memory 存放 open/close/high/low/volume 数组。
- 并发粒度按 `roll_d` 分配，一个任务计算一个 rolling window。
- 主进程收集每个 rolling window 的结果，再按当前逻辑 inner merge。

第二阶段自动规则：

```text
roll_work_units = roll_window_count * product_count * trading_day_count * avg_metric_count

if roll_window_count < 3:
    rolling_parallel = false
elif roll_work_units < 500000:
    rolling_parallel = false
else:
    rolling_parallel = true
```

worker 数：

```text
workers = min(cpu_cap, roll_window_count, user_cap, memory_cap)
```

不建议第一阶段按产品切片并发：

- 当前计算类大量按二维数组对所有产品向量化计算。
- 按产品切片会增加结果拼接复杂度。
- 产品切片更适合作为极大产品数或内存不足时的后续优化，而不是默认策略。

### 智能体执行协议

智能体使用该 skill 计算指标时，应遵循固定流程：

1. 读取 `SKILL.md` 和必要 references。
2. 生成或读取 `job.json`。
3. 运行 `--dry-run`。
4. 如果 dry-run 有阻断项，先修复输入或向用户说明。
5. 如果 dry-run 只有 warning，简要告知用户风险，再运行 `--execute`。
6. 执行后读取 `run_manifest.json` 和输出 parquet schema。
7. 回答用户时报告输出路径、产品数量、区间/window 数量、是否并发、worker 数、关键 warning。

智能体不应：

- 直接根据自然语言猜测 `num_workers`。
- 在 `spec_end_date` 单日任务上默认开启区间多进程。
- 对 rolling 指标声称已经使用 `num_workers` 并发。
- 在没有 dry-run 计划的情况下覆盖已有 parquet。
- 在 `price_basis=unknown` 时给出确定性绩效结论。

### SKILL.md 应新增的智能体入口说明

当入口脚本落地后，`SKILL.md` 需要新增：

- 优先使用 `run_metrics_job.py --dry-run`，不要临时写一次性调用脚本。
- 自动并发只对区间指标可靠；rolling 并发需要等待实现。
- 区间多进程按 period 内 end_date 并行，`spec_end_date` 单日通常不并发。
- 并发决策必须写入 manifest。
- 用户问“为什么用了 N 个进程”时，回答 manifest 中的 `parallel_decisions.reason`，不要凭经验解释。

## V2 可分享可移植技能设计

### 设计目标

V2 的目标是让 `skills/metrics-factory` 可以独立分享并安装到任意电脑的 Codex skills 目录，同时仍能操作某个本地 MetricsFactory 源码目录。

必须支持两种部署模式：

- 项目内模式：skill 位于 `MetricsFactory/skills/metrics-factory`，从项目根目录运行。
- 全局模式：skill 位于 `~/.codex/skills/metrics-factory` 或其他 skills 根目录，MetricsFactory 源码通过 `--project-root`、环境变量或当前目录发现。

V2 不把 Python 环境、仓库绝对路径、macOS/Homebrew 路径写进技能协议。环境可以由用户提前准备，也可以由智能体自动创建，但自动安装必须限制在项目局部 venv。

### 可移植边界

skill 包应只包含：

- `SKILL.md`
- `agents/openai.yaml`
- `scripts/*.py`
- `references/*.md`

不应包含：

- `__pycache__`
- `.venv` 或 `.metricsfactory-venv`
- 本机临时输出
- 本机绝对路径
- 用户私有 pip 源 token 或代理配置

### 项目根发现规则

所有脚本统一支持 `--project-root`。

项目根判定标准：

- 目录下必须同时存在 `metrics_factory.py`、`metrics_cal_config.py`、`period_metrics_cal.py`、`rolling_metrics_cal.py`。

查找顺序：

1. CLI 参数 `--project-root`
2. 环境变量 `METRICS_FACTORY_PROJECT_ROOT`
3. 当前工作目录向上查找
4. 脚本所在目录向上查找

全局 skill 模式通常必须传 `--project-root`，除非当前工作目录已经在 MetricsFactory 源码树内。

### Python 解释器策略

文档中使用占位符 `<python>`，不写死 `.venv/bin/python`。

解释器选择顺序：

1. 用户明确提供的 Python 路径
2. 环境变量 `METRICS_FACTORY_PYTHON`
3. 当前激活环境的 `sys.executable`
4. `<project-root>/.metricsfactory-venv/bin/python`
5. `<project-root>/.venv/bin/python`
6. PATH 中的 `python3`

运行前必须用 `check_runtime.py` 检查：

- Python 版本建议为 3.11 或 3.12。
- Python 架构必须与 native wheels 一致。
- 必须能 import `numpy`、`pandas`、`scipy`、`numba`、`pyarrow`、`tqdm`、`dateutil`。
- `psutil` 可选，但建议安装；没有时只影响内存感知和并发保守估算。
- 必须能 import MetricsFactory runtime。

### 自动安装策略

新增 `scripts/setup_runtime.py`。

默认行为：

- 在 `<project-root>/.metricsfactory-venv` 创建隔离环境。
- 不安装到系统 Python。
- 不安装到用户全局 site-packages。
- 安装完成后自动运行 `check_runtime.py`。

依赖建议：

```text
numpy>=1.26,<2.1
pandas>=2.2,<3.1
scipy>=1.11
numba>=0.60
pyarrow>=15
python-dateutil>=2.8
tqdm>=4.60
psutil>=5.9
```

安装命令由脚本执行，支持：

- `--python` 指定用哪个解释器创建 venv。
- `--venv` 指定 venv 目录，默认 `.metricsfactory-venv`。
- `--index-url` 传入企业或镜像源。
- `--extra-index-url` 传入补充源。
- `--no-install` 只创建 venv 不安装依赖。

### MetricsFactory 包名兼容

当前业务代码使用 `MetricsFactory.*` 绝对导入。为了允许源码目录不叫 `MetricsFactory`，运行脚本应在导入前注册 package alias：

```python
module = types.ModuleType("MetricsFactory")
module.__path__ = [str(project_root)]
sys.modules["MetricsFactory"] = module
```

这样 `from MetricsFactory.metrics_factory import ...` 可以在任意目录名下运行。

### 脚本职责

`check_runtime.py`：

- 接收 `--project-root`。
- 输出 JSON。
- 只检查，不安装，不修改文件。
- exit code：0 表示可运行，2 表示 blocker。

`setup_runtime.py`：

- 接收 `--project-root`。
- 创建项目局部 venv。
- 安装依赖。
- 调用 `check_runtime.py` 做最终验证。
- 输出 JSON。

`run_metrics_job.py`：

- 增加 `--project-root`。
- 继续支持当前目录自动发现。
- runtime import 失败时提示优先运行 `check_runtime.py` 或 `setup_runtime.py`。
- stdout 保持 JSON；核心计算日志转 stderr。

`export_metric_catalog.py`：

- 继续用 AST 静态解析。
- 全局模式下必须支持 `--project-root`。

### SKILL.md 改造

`SKILL.md` 只保留核心决策和命令模板：

```bash
python <skill-dir>/scripts/check_runtime.py --project-root <project-root>
python <skill-dir>/scripts/setup_runtime.py --project-root <project-root>
python <skill-dir>/scripts/run_metrics_job.py --project-root <project-root> --request job.json --dry-run
python <skill-dir>/scripts/run_metrics_job.py --project-root <project-root> --request job.json --execute
```

环境细节移到 `references/environment.md`。

`job-schema.md` 中也要使用 `<python>`、`<skill-dir>`、`<project-root>` 占位符，不使用本机路径。

### 人类决断点

仍需要人类或调用方决定：

- 是否允许自动创建项目局部 venv。
- 是否使用企业私有 pip index。
- 是否接受 rolling open/close 风险。
- 是否接受 `price_basis=unknown`。
- 是否允许覆盖已有输出。

这些都不应由 skill 静默决定。
